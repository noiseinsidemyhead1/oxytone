# oxytone — notes pour Claude Code

Anciennement **ytmr** (renommé le 2026-11-02, voir « Renommage » en fin de fichier).

Client YouTube Music natif en Rust (CachyOS + Windows 11). Le plan de référence est `oxytone-plan.md` : l'architecture, les choix techniques et l'ordre des phases y sont fixés.

## Règles du projet

- **Une phase à la fois.** En fin de phase : résumé, commandes de validation, puis attendre l'accord de l'utilisateur.
- **Jamais d'extraction de flux YouTube** (signature, `n`, PO tokens). La lecture passe exclusivement par mpv (processus fils, JSON IPC) ; les adresses viennent de yt-dlp. Seule exception assumée : le cache audio télécharge l'adresse que yt-dlp a donnée (rien n'est déchiffré par oxytone).
- `oxytone-core` est la seule source de vérité. La GUI et l'API envoient des commandes et s'abonnent aux événements (`broadcast` pour les événements, `watch` pour l'état courant). Aucune logique métier dans la GUI ou l'API.
- Lecture derrière un trait async `Player`.
- **GUI native iced 0.14** (`oxytone-gui`), **rendu GPU (wgpu, DX12 sous Windows)**. Une interface web (webview) a été essayée et **refusée par l'utilisateur** (« une autre app pas performante ») : ne pas y revenir. Le rendu logiciel tiny-skia a été essayé puis abandonné (saccades). La GUI parle directement au `CoreHandle` (même processus) ; l'API ne sert qu'au CYD et aux télécommandes. Priorités de l'utilisateur : rapidité, légèreté, design soigné avec jaquettes, animations douces.
- N'inventer aucune API de crate : `cargo add`, puis vérifier les signatures dans `~/.cargo/registry/src` ou sur docs.rs (critique pour ytmapi-rs, souvlaki, iced et `windows`).
- Pas de `unwrap()`/`expect()` hors tests (lint clippy du workspace). `thiserror` dans les libs, `anyhow` dans les binaires, logs avec `tracing`.
- `#[cfg(windows)]` / `#[cfg(unix)]` uniquement là où c'est inévitable (IPC mpv, intégration Windows de `oxytone-os`). Chemins via `directories` (`oxytone_core::AppPaths`).
- `unsafe` interdit au workspace (`unsafe_code = "deny"`), autorisé seulement module par module avec `#![allow(unsafe_code)]` et un commentaire : `set_var` au démarrage, `oxytone_os::taskbar`, `oxytone_os::tray`, `oxytone_os::fullscreen`, `oxytone_os::secret` (DPAPI), registre des notifications.
- Chaque module non trivial commence par un commentaire `//!` qui explique son rôle en langage simple (« En clair : … »).
- API : `127.0.0.1:26540` par défaut ; token Bearer obligatoire hors localhost ; pas de CORS permissif ; bornes strictes (volume 0-100, seek, jaquette ≤ 320 px).
- **Ne jamais simuler clavier/souris quand l'utilisateur se sert de l'appli**, ni fermer / relancer son instance sans son accord. Ne pas modifier son compte YouTube (likes, abonnements, playlists) pour tester sans son accord : la lecture seule est libre.

## Conventions

- Workspace Cargo, édition 2024, resolver 3. Les métadonnées et les lints sont hérités du workspace (`version.workspace = true`, `[lints] workspace = true`).
- Dépendances déclarées crate par crate (via `cargo add -p <crate>`).
- Code, commentaires et messages d'erreur en français ; identifiants en anglais.
- Commits : identité `noiseinsidemyhead1` / noreply (configurée dans `.git/config`), **pas de ligne Co-Authored-By**.
- **Encodage** : ne jamais réécrire un fichier source avec `Get-Content`/`Set-Content` de PowerShell 5.1 (lu en ANSI → accents doublement encodés, « Ã© »). Passer par Python (UTF-8, `newline="\n"`) ou l'outil d'édition. Dans Git Bash, un heredoc contenant des apostrophes peut échouer : écrire le script dans un fichier.
- PowerShell : `-match` ignore la casse (« 0 failed » correspond à « FAILED ») → `-cmatch`.

RUST_LOG=warn,oxytone::timing=debug cargo run --release -p oxytone-cli -- bench-cold [--account] [--client android] [--skip 10]   # démarrage à froid : médiane / p90

Sous Windows, compiler depuis PowerShell : dans Git Bash, `/usr/bin/link` masque le `link.exe` de MSVC. Si l'utilisateur a oxytone ouvert, `target/release/oxytone.exe` est verrouillé : compiler dans un autre dossier (`--target-dir target/alt`).

**CI :** `.github/workflows/ci.yml` existe, mais GitHub Actions est bloqué sur le compte (`startup_failure` même sur un workflow vide, quota non épuisé). La validation de fin de phase se fait donc **en local sur Windows ET sur CachyOS** (`cargo build`, `clippy`, `test`).

## Lecture (`oxytone-player`, `oxytone-core`)

- **En-têtes géants de Google (31/10/2026)** : music.youtube.com renvoie `connection-allowlist-report-only` (liste de tous les domaines Google, > 10 Ko) ; le client HTTP/2 de Rust plafonne les en-têtes de réponse à 16 Ko → « error sending request » (connexion et TLS réussis, curl fonctionne). Tous les clients reqwest passent par `oxytone_catalog::http_builder()` (`http2_max_header_list_size` 256 Ko) ou posent la même option (pochettes, cache audio). Ne jamais créer un `reqwest::Client::new()` nu.
- **Consentement RGPD** : depuis l'UE, `music.youtube.com` redirige vers `consent.youtube.com` (400, corps vide) et ytmapi-rs échoue avec « Unable to parse ytcfg ». `oxytone-catalog` envoie le cookie `SOCS=CAI` via un client reqwest passé à `YtMusicBuilder::new_with_client` (feature `reqwest` de ytmapi-rs).
- **Qualité contre vitesse (sans compte)** : seuls les clients yt-dlp par défaut (TV/visionOS) donnent de l'audio seul (Opus 251, ~160 kb/s), mais l'URL n'est utilisable qu'à `available_at` (~5 s après la résolution ; avant, 403). `android`/`tv_simply`/`web_music` sont immédiats mais ne donnent que le format 18 (AAC ~96 kb/s). D'où `oxytone_player::resolve` : **préchargement** en `StartMode::Quality`, **démarrage à froid** en `StartMode::Fast` (`player.fast_start_client`, `android` par défaut). Tester un client : `yt-dlp -J -f bestaudio/best --extractor-args youtube:player_client=<c> <url>`.
- **Premium** (`player.cookies_from_browser = "firefox"`) : format 774 (Opus ~256 kb/s) ou 141 (AAC), sans délai `available_at`. Client `web_music` + `player_skip=webpage,configs`. Le mode rapide est désactivé (les clients rapides n'acceptent pas les cookies). Chrome/Edge sous Windows : cookies chiffrés, illisibles par yt-dlp.
- **Worker yt-dlp** (`oxytone_player::worker`) : processus Python permanent (environnement privé `cache_dir/ytdlp-env`, créé par `ensure_env`, ~32 s la toute première fois) ; le résolveur bascule dessus dès qu'il est prêt, sinon sur l'exécutable. **Lancement** (`worker::launch`) : le worker démarre tout de suite avec l'environnement existant (~0,6 s ; avant, `has_yt_dlp` ou `pip` passaient d'abord : ~1-1,5 s, et **11-14 s les jours de nouvelle version de yt-dlp**, mesuré le 2026-11-02). S'il ne démarre pas : `pip --force-reinstall` (un `--upgrade` ne fait rien si les métadonnées de yt-dlp sont restées), sinon environnement recréé (aussi quand Python de l'environnement ne répond plus, ex. interpréteur déplacé). **Mise à jour quotidienne en fond** (`worker::update_if_due`, priorité basse, après « worker prêt ») ; si la version change, un nouveau worker la charge et remplace l'ancien (`backend::update_worker`) : les résolutions en cours finissent sur l'ancien, arrêté quand sa dernière référence part. Une résolution pendant `pip` réussit sur l'ancien worker (vérifié). Sous Windows, pip renomme en `~…` une bibliothèque compilée chargée (`.pyd` de pycryptodomex) sans pouvoir l'effacer : `remove_pip_leftovers` la supprime à la mise à jour suivante. Test réel : `OXYTONE_TEST_ENV=<dossier jetable> cargo test -p oxytone-player --release -- --ignored --nocapture launch_then_update`. Tout yt-dlp de fond tourne en priorité basse. Adresses résolues gardées dans `cache_dir/streams.json` (valables plusieurs heures).
- **Démarrage à froid** (mesuré le 2026-10-30) : par morceau, yt-dlp passait ~1 s sur « initial data » (qui ne sert qu'à savoir si le compte est Premium), ~1 s sur le défi JavaScript et ~0,3 s sur le reste. Le worker détecte Premium **une fois** au lancement (`op: premium`) puis saute cette requête (remplacement de `YoutubeIE._is_premium_subscriber` / `_download_initial_data`, sous `try` : si yt-dlp renomme, rien ne change). `player_skip=initial_data` seul ferait perdre le format Premium (18 au lieu de 774). Résultat : ~1,5-1,9 s par morceau au lieu de 2,2-3 s.
- **Mesure du démarrage à froid** (`oxytone-cli bench-cold`, 10 morceaux jamais résolus, sans cache, mpv à volume 0 ; spans `résolution` et `démarrage_à_froid`, résumés sur la cible `oxytone::timing` ; `PlayerEvent::Restarted` = `playback-restart` de mpv, le son sort). Le démarrage à froid demande `StartMode::Fast` ; **il passe toujours par le worker** dès qu'il est prêt (`YtDlpResolver::worker_for`), l'exécutable n'est qu'un repli. Sans compte, la requête porte le client rapide (`"client": "android"`) : le worker le pose dans `extractor_args` de l'instance yt-dlp de son fil pour cette requête (yt-dlp les relit à chaque extraction), puis remet ceux du lancement pour la suivante (vérifié : android → 18, défaut → 251, en alternance dans le même fil). Avant (corrigé le 2026-11-02), `Fast` passait toujours par `yt-dlp.exe` (~1,25 s rien qu'à démarrer), qui ne reçoit pas la session de « Se connecter » : avec compte, lecture sans compte, format 251 et ~4 s d'`available_at`. Avec cette session, si le worker n'est pas encore branché, le résolveur l'attend jusqu'à 15 s (`WORKER_WAIT`) plutôt que de jouer sans compte. Mesures (Windows, 2026-11-02, médiane / p90) :
  - sans compte, `android` : avant (exécutable) résolution 2 974 / 3 293 ms, mpv 736 / 948 ms, total 3 609 / 4 097 ms ; **après (worker) : résolution 1 176 / 1 264 ms, mpv 363 / 531 ms, total 1 487 / 1 818 ms**, format 18 (combiné AAC ~96 kb/s).
  - avec compte, avant la correction : 8 472 / 8 809 ms (format 251) ; **après : résolution 923 / 1 363 ms, mpv 363 / 605 ms, total 1 537 / 1 595 ms, format 774**.
- **Voie directe `/youtubei/v1/player` sans yt-dlp : essayée puis abandonnée** (2026-11-02, 10 morceaux, prototype hors du dépôt). `IOS` 21.26.4 (version de yt-dlp) : formats sans `url` ni `signatureCipher`, seulement `serverAbrStreamingUrl` (SABR). `IOS` 20.10.4 (celle de `Catalog::loudness`) : 140 / 251 en clair, requête en ~0,2 s, mais **403 au-delà de la première requête** (milieu et fin du fichier, encore après 15 s d'attente) : PO token exigé (yt-dlp : `GVS_PO_TOKEN_POLICY` requis pour `ios` / `android`). `ANDROID_MUSIC` (`music.youtube.com`, versions 7.27 à 8.44) : `LOGIN_REQUIRED`. Aucun format audio lisible en entier : ne pas y revenir sans PO token (hors périmètre).
- **Moteur JS** : node est préféré à deno (mesuré : 1,45 s contre 1,64 s par morceau) ; yt-dlp n'active que deno de lui-même, donc node est demandé explicitement (`js_runtimes`). deno n'est pas installé chez l'utilisateur.
- **Préchargement** : le core résout le suivant dès que le courant démarre et l'ajoute à la playlist de mpv (`loadfile … append`, `--prefetch-playlist`, `--gapless-audio`) ; mpv enchaîne seul (~7 ms entre `end-file` et `playback-restart`). « Suivant » vers une entrée préchargée = `playlist-next`.
- **Démarrage à froid seul** : tant que le morceau demandé n'a pas démarré (`current_entry` vide, `Status::Loading`), rien d'autre n'est résolu (`pump_warm` attend, `start` n'appelle `refresh_lookahead` que si le morceau est déjà prêt) ; anticipation et préchargement partent de `on_started`. Avant, les 10 suivants partaient en même temps dans le même worker (GIL de Python, réseau) : 4-5 s au lieu de ~1,5 s. Un préchargement échoué n'est pas retenté pour la même entrée (`preload_failed`) : hors ligne, il était relancé des centaines de fois par seconde.
- **Anticipation** : les 10 morceaux après le suivant sont résolus en file de fond (`Priority::Background`, 2 yt-dlp) ; le suivant et les clics passent en `Priority::Urgent` (2 autres). Une vidéo en cours de résolution est partagée (`inflight`). Survol d'un morceau 250 ms → `Command::Prefetch`. Mesuré : skip vers un morceau anticipé ≈ 0,06 s, clic sur un morceau préchargé → son en ~0,4 s.
- **Cache audio** (`oxytone_player::audio_cache`) : chaque morceau résolu en qualité haute est téléchargé en fond (morceaux de 1 Mo avec `Range` et le User-Agent de yt-dlp, taille lue dans `clen=`) vers `cache_dir/audio/<id>.audio` ; `Resolver::cached` le rend en premier. Limite `player.audio_cache_mb` (2 048 par défaut, 0 = désactivé), les moins récemment écoutés partent en premier.
- **Effets audio** (`oxytone_player::effects`) : égaliseur 10 bandes ±12 dB, propriété `af` de mpv (`lavfi=[volume=-XdB,equalizer=…]`). `Command::SetEffects`, gardés dans la session.
- **Volume homogène** : comme YouTube Music, un gain fixe par morceau (jamais positif) ramène les morceaux trop forts à -14 LKFS. Le niveau vient de la réponse « player » du **client iOS** (`Catalog::loudness`, `playerConfig.audioConfig.trackAbsoluteLoudnessLkfs`, métadonnées seulement) : les clients WEB / WEB_REMIX / MWEB répondent « UNPLAYABLE » sans ces données (constaté le 2026-10-30). Filtre étiqueté `@oxytonegain:lavfi=[volume=1]` en fin de chaîne `af`, réglé par `af-command oxytonegain volume <linéaire> volume` à chaque morceau (`Player::set_gain`) ; gain du suivant demandé d'avance (`Radio::loudness`, `want_gain`), 0 dB tant qu'il n'est pas connu.
- **Qualité** (`QualityPreference`) : Maximale (`bestaudio/best`, 774 avec Premium), Haute (`abr<=160`, 251), Économe (`abr<=70`, 250). `Command::SetQuality`, gardée dans la session ; changer vide le cache d'adresses. Le worker reçoit le format à chaque requête et refait son sélecteur quand il change (yt-dlp le fige à la création : `format_selector = build_format_selector(fmt)`). Vérifié : 250 / 774 en alternance dans le même worker.
- **Sortie audio** : la liste est demandée à mpv au démarrage du moteur (`Player::audio_devices` : son premier envoi spontané arrive avant que le moteur écoute, d'où le « Chargement… » sans fin d'avant), puis suivie par l'observation de `audio-device-list` (→ `PlayerEvent::AudioDevices`) ; `Command::SetAudioDevice` → propriété `audio-device` (`auto` = celle du système), gardée dans la session.
- **Hors ligne** : `Command::KeepOffline { video_ids, keep }` → les morceaux sont épinglés dans le cache audio (`pinned.json`, jamais effacés par la limite de taille ni par « Vider ») et résolus en file de fond **après** l'anticipation (`offline_wanted`), ce qui déclenche leur téléchargement ; une adresse déjà connue est téléchargée tout de suite. GUI : bouton « Hors ligne · n / m » dans l'en-tête d'une playlist, playlists gardées dans `cache_dir/library/offline.json` (redonnées au moteur au lancement et à chaque mise à jour), relevé du dossier audio toutes les 4 s tant que des morceaux manquent (arrêt après ~1 min sans progrès), icône sur les lignes disponibles sans réseau ; bouton « Télécharger » → « Téléchargement · n / m » → pastille pleine « Téléchargée ». Morceau seul : clic droit « Télécharger » (`cache_dir/library/downloads.json`) ; album : bouton de l'en-tête (`Lib::DownloadAlbum`, ses morceaux vont dans `downloads`, l'album n'entre pas dans la bibliothèque ; `library::download_pill` partagé avec les playlists). Playlist virtuelle « Téléchargés » (`library::DOWNLOADS_ID`) = **tout** ce qui est sur le disque : morceaux seuls + ceux des playlists téléchargées (`offline_lists`), filtrés sur `offline_ids` ; image = mosaïque 2 × 2 des pochettes (l'utilisateur n'aime pas l'icône de téléchargement ni la coche : « Téléchargée » = pastille pleine, texte seul).
- **Mode hors ligne** (Paramètres, `ui.json`) : `Command::SetOffline` → le résolveur ne rend que les fichiers du cache audio (`Resolver::set_offline`), ni radio ni gain ; `Covers::set_offline` (plus de téléchargement de jaquettes) ; côté GUI `App::catalog()` et `LibraryState::ready()` rendent `None` (aucune requête), accueil = « Téléchargés » + playlists téléchargées, lignes filtrées sur `offline_ids` (`view_order`, `LibraryState::playable`). En passant hors ligne : le moteur retire de la file ce qui n'est pas sur le disque (`drop_unavailable_offline`, le morceau en cours compris) ; la GUI abandonne les chargements en cours (`pending_route`, `streaming`), n'attend jamais une page (`needs_loading` faux hors ligne et pour « Téléchargés » : sinon barre de chargement sans fin), refuse albums / artistes, paroles « indisponibles hors ligne ». Jaquettes : l'autre taille déjà sur le disque sert de secours.
- **Morceaux grisés** : `Track::unavailable` (`musicItemRendererDisplayPolicy = …GREY_OUT` dans les playlists) : affichés en gris, jamais lancés (le moteur les retire de `PlayTracks` / `Enqueue`…).
- **Écoutes YouTube** : `Track::plays` (« 12 M de lectures »), lu sur les pages d'album et les titres populaires d'artiste, affiché **seulement** sur les routes Album / Artist (un morceau liké depuis un album garde son champ : il ne doit pas s'afficher dans une playlist).
- **« Téléchargé » = épinglé** (`pinned.json` du cache audio) **et** présent : le cache automatique des écoutes récentes n'est jamais présenté comme téléchargé (`scan_offline` croise les deux ; hors ligne, `Resolver::cached` ne rend que les épinglés). Libérer des morceaux (`keep_offline` de la GUI) épargne ceux encore voulus par « Téléchargés » ou une autre playlist. Pastille des lignes : rond plein de la teinte avec flèche sombre (`views::downloaded_badge`).
- **Statistiques** (`oxytone_core::stats`, journal relâché en quittant la page) : le moteur ajoute une ligne à `data_dir/plays.jsonl` quand 75 % d'un morceau a été écouté (30 s si sa durée est inconnue). `stats::summarize` (dans le core) : temps d'écoute, écoutes, titres et artistes différents, classements, temps par jour, série de jours ; page `Route::Stats` (barre latérale) avec 7 jours / 30 jours / 12 mois / tout.
- **Fondu enchaîné : retiré** (demande de l'utilisateur) : mpv ne lit qu'un flux, on n'obtenait qu'un fondu de sortie puis d'entrée sans superposition. Un vrai fondu exigerait deux mpv. Pour mémoire : un filtre étiqueté se pilote par `af-command <label> volume <g> volume` (la cible est obligatoire).
- **Session** : `data_dir/session.json` (file ≤ 500 titres, morceau courant, position, volume, repeat, aléatoire, radio, effets), écrite à l'arrêt, reprise au lancement (en pause, même position).
- **User-Agent** : l'URL signée exige le User-Agent renvoyé par yt-dlp ; passé en option par fichier dans `loadfile` (`user-agent=%<octets>%<valeur>`, à cause des virgules).
- **Fenêtres console** : tout programme console lancé depuis l'appli passe par `oxytone_player::process::command` (`CREATE_NO_WINDOW`), sinon un terminal noir s'ouvre.
- **stdin tokio** : la lecture de stdin bloque un thread ; la CLI termine avec `runtime.shutdown_background()`.
- **PATH** : après `scoop install`, les shells déjà ouverts ne voient pas mpv ; ouvrir un nouveau terminal.

### File d'attente (`oxytone-core::queue`, `engine`)

- Historique (caché, pour « précédent ») + courant + suite, et un **contexte** (liste d'origine + ajouts). Lancer un titre au milieu d'une playlist met la fin puis le début dans la suite (rien n'est « joué »). La file publiée (`QueueSnapshot`) commence au morceau en cours (`current = Some(0)`). Sans historique, « précédent » = titre d'avant dans le contexte (`prepare_previous`).
- Activer / couper l'aléatoire **reconstruit** la suite depuis tout le contexte. `Command::PlayShuffled` (`Queue::replace_shuffled`) mélange toute une liste depuis une page.
- **Le morceau en cours n'est jamais remis dans sa propre suite** (`Track::same_song` : même identifiant, ou même titre sans parenthèses + même artiste principal, clip / version audio). La radio automatique écarte aussi le morceau en cours et toute chanson déjà dans la file.
- **Répétition de la file** : le tour suivant n'est ajouté qu'au passage au morceau suivant (`advance_auto`), jamais par `set_shuffle` / `set_repeat` : sinon une file vide en répétition voyait réapparaître le morceau en cours au moindre changement (test `toggling_shuffle_never_adds_the_playing_track`).
- **Radio** : réactiver l'autoplay remet la graine à zéro ; si une radio n'apporte que des doublons, nouvelle graine parmi les 30 derniers titres (3 essais). En aléatoire, ses titres sont répartis dans la suite (`append_mixed`), le prochain (préchargé) ne bouge pas.

## API (`oxytone-api`)

Base `http://127.0.0.1:26540/api/v1`. Lecture : `GET /state`, `POST /toggle|play|pause|next|prev`, `POST /seek {position_ms}`, `/volume {value}`, `/shuffle {on}`, `/repeat {mode: off|all|one}`, `/autoplay {on}`, `/like` (501 : pas encore branché). File : `GET /queue?offset&limit`, `POST /queue/play {tracks,start}`, `/queue/add {tracks}`, `/queue/next {tracks}`, `/queue/jump {id}`, `/queue/remove {id}`, `/queue/move {id,to}`, `/queue/clear`. Catalogue : `GET /search?q=`, `/album/{id}`, `/artist/{id}`. `POST /prefetch {video_id}`. Jaquettes : `GET /cover/{id}?size=&fmt=jpg|rgb565` (jpg ≤ 1200 px, rgb565 ≤ 320 px pour le CYD, `Cache-Control: immutable`), `GET /cover/{id}/accent`. `WS /ws` : `state`, `position` (1 Hz), `track_changed`, `queue_changed`, `error`.

Sécurité (`security.rs`) : `Host` limité aux noms de loopback en mode local (anti DNS rebinding), `Origin` étranger refusé (anti CSRF), token Bearer (ou `?token=`) dès que `bind` n'est pas loopback ou `require_token = true`. Les URL de jaquettes reçues des clients sont filtrées sur les domaines YouTube/Google (anti SSRF).

## Catalogue et compte (`oxytone-catalog`)

- **ytmapi-rs 0.3.3 est souvent trop strict** : on renvoie la même requête et on lit le JSON brut (`raw::RawPost`, `raw.rs`). Cas traités : recherche de titres (« Expected Song result »), en-tête des playlists des autres (« straplineTextOne / facepile »), page d'artiste sans photo d'en-tête (`artist_raw`), accueil (`home.rs`, `FEmusic_home` + 3 suites, contexte `hl=fr`), historique, profil (`account/account_menu`), pagination des playlists (jeton de continuation ré-encodé par ytmapi-rs → requête maison `NextPage`), `setVideoId` des morceaux (exigé pour retirer), suggestions de playlists courtes ignorées.
- **Connexion (Windows)** : « Se connecter à YouTube » (barre latérale, Paramètres, pages qui exigent le compte) lance `oxytone --login` (`apps/oxytone/src/login.rs`, `tao` + `wry`/WebView2, navigation privée) : page de connexion Google ; dès que music.youtube.com a `SAPISID`, les cookies sortent en JSON sur stdout et la fenêtre se ferme. La GUI les chiffre (DPAPI, `oxytone_os::secret`) dans `data_dir/youtube-session.bin` et **redémarre** (`--relaunch` : la nouvelle instance attend que le port 26541 se libère). Au démarrage, `backend::load_session` → `ResolverOptions::session` : en-tête du compte (`session::cookie_header`), cookies rangés dans le pot de yt-dlp par le worker (`oxytone_cookies`, qualité Premium), pas de démarrage rapide. « Se déconnecter » efface le fichier. Choix de l'utilisateur : ne pas supposer Firefox (Chrome / Edge / Brave chiffrent leurs cookies sous Windows, illisibles par yt-dlp). Risque : Google peut refuser la connexion dans une fenêtre intégrée.
- **Ancienne voie** (toujours lue, Linux) : `cookies_from_browser = "firefox"` → cookies lus **par le worker** (`Worker::browser_cookie`), en mémoire seulement. `Account` a un `Debug` manuel pour ne jamais logger le jeton.
- **Identifiants de playlist** : lecture = `VL<id>`, modifications = id nu (`bare_id`, `browse_id`, `edit_id`). Titres likés : `LM`. Listes de podcasts `RDPN…` écartées.
- **Abonnement à un artiste** : le bouton de la page vise souvent une *autre* chaîne que l'identifiant de la page (constaté : page `UC59RK…`, abonnement `UCiRWTc0…`) ; ytmapi-rs envoyait l'identifiant de la page → 400 « Error unsubscribing ». `Account::follow_artist` lit la page, prend `subscribeButtonRenderer.channelId` et les `params` de l'action, et envoie la requête lui-même.
- **Likes d'albums** = `rate_playlist` sur la playlist audio `OLAK5uy…` (`Album::audio_playlist_id`) ; playlist d'un autre = `rate_playlist`. Retrait groupé : `Account::remove_tracks` (une seule lecture de la playlist).
- **Paroles** (`lyrics.rs`) : en parallèle LRCLIB (`/api/get`, `/api/search` par champs et en texte libre), NetEase (`music.163.com/api/search/get` + `song/lyric`, crédits chinois retirés) et YouTube Music (texte simple : ses horodatages Musixmatch ne sont rendus ni au client web, même connecté, ni au client Android). Classement : synchronisées à ±3 s de la durée > texte simple > synchronisées d'une autre version.
- **Cartes de morceaux de l'accueil** : le sous-titre peut commencer par le type (« Titre • Xtrullor • The 1st Era », « Titre » = morceau) : `home::is_type_label` l'écarte ; artiste = groupe lié à une chaîne `UC…`, album = segment `MPRE…`.
- **Notifications Windows** : `tauri-winrt-notification` directement (pochette en `appLogoOverride`, petite à gauche, sans son) ; notify-rust posait l'image en grand. notify-rust reste pour Linux.
- **Import Spotify** (`spotify.rs`, GUI `import.rs`, bouton « Importer depuis Spotify » de la Bibliothèque) : lien de playlist **publique** lu sur `open.spotify.com/embed/playlist/<id>` (`__NEXT_DATA__` → `trackList`, **100 titres au plus**, sans compte développeur), ou **CSV d'Exportify** déposé sur la fenêtre (`window::Event::FileDropped`, colonnes repérées par leur nom). Chaque titre cherché (« titre artiste principal », 6 en parallèle, paquets de 10 pour la progression), meilleur résultat noté sur titre / artiste / durée (`best_match`, seuil 3). Mesuré : 20 / 20 trouvés en 3,8 s. Playlist privée créée puis remplie par paquets de 100. La création n'a pas été essayée sur le vrai compte (modification : accord de l'utilisateur).
- **Album d'un morceau** : un clic sur un titre ouvre toujours son album ; sans `album_id` (radio, accueil), `Catalog::album_of` le cherche (même vidéo, sinon même chanson).
- **Suggestions** : `Catalog::suggestions` (`get_search_suggestions`). **Radio d'un titre** : `Catalog::radio` (YouTube met le titre de départ en tête).
- **Démarrage sans réseau** : `Catalog::new()` ne se connecte qu'à la première utilisation (`OnceCell`, 3 essais).
- Chaque morceau lancé est signalé à YouTube (`report_play`), une fois par entrée de file. Déconnexion propre à oxytone (fichier `cache_dir/library/disconnected`, la session Firefox n'est pas touchée).

## GUI (`oxytone-gui`)

### Organisation

- `app/` : état et messages (architecture Elm). `mod.rs` (structure `App`, types, démarrage, abonnements), `update.rs` (le `match` des messages + `aim_anims`), `covers.rs` (pochettes, mémoire, teintes), `navigation.rs` (pages, recherche, lectures depuis une page), `selection.rs` (sélection, glisser-déposer, raccourci L), `keys.rs`, `lyrics.rs`, `core_sync.rs` (état / file du moteur), `native.rs` (HWND), `fade.rs` (fondus de couleur).
- `views.rs` (widgets), `library.rs` (compte, playlists, accueil, historique), `collection.rs` (bibliothèque : albums, artistes, tri, likes), `context.rs` (menu clic droit + `PointCatcher`), `settings.rs`, `chrome.rs` (barre de titre), `anim.rs` (curseurs, interrupteurs, fondu de la file), `smooth.rs` (défilement animé), `style.rs`, `icons.rs`, `backend.rs` (démarrage / arrêt de mpv, catalogue, core, API).
- La fenêtre s'ouvre tout de suite ; le backend démarre dans un `Task` (`Message::BackendReady`). Fermer la fenêtre (`exit_on_close_request: false`) arrête d'abord mpv proprement. Les changements du core arrivent par `Task::stream(core_updates)` (watch + broadcast).

### Règles qui ont coûté cher

- **Ne jamais mettre une liste dans le message d'une ligne ou d'un en-tête** (`Message::Play(tracks.clone(), i)` dans 1 189 lignes = 1,4 M de copies par image → 0 im/s) : un indice (`Lib::PlayAt(i)`) ou un identifiant (`Lib::AddToPicked(id)`).
- **Arbre de widgets stable** (`views::view`) : page, fenêtre d'ajout, message, aide, barre de titre, bords, menu et étiquette de glisser-déposer sont *toujours* présents (une couche `Space` quand il n'y a rien). Ajouter un `stack!` autour de la page à l'ouverture d'un menu faisait recréer la page : toutes les listes défilantes repartaient en haut.
- **Survol** : la sortie d'une ligne n'efface le survol que s'il la concerne (`Unhover(video_id)`, `QueueUnhover(i)`, `CardUnhover`, `DropLeave`) : en remontant, iced envoie l'entrée de la nouvelle ligne *avant* la sortie de l'ancienne. Les fenêtres par-dessus sont `opaque` et les `Hover` sont ignorés tant qu'elles sont ouvertes (sinon survol de la page dessous + préchargements yt-dlp en rafale = 5 im/s).
- **Clavier** : dans iced 0.14, `KeyPressed::key` est la touche *sans* Maj ; en AZERTY, « / » et « ? » ne se lisent que sur `modified_key`. `keyboard::listen` ne transmet que les touches ignorées par les widgets.
- **Opacité** : iced n'a pas d'opacité de calque. Fondus = voile de la couleur du fond posé par-dessus (barre de la vue « En cours », file remélangée) ; ça ne marche que sur un fond uni.
- Un bouton iced ne centre pas son contenu verticalement (pastille des interrupteurs : marge égale tout autour). iced ne coupe pas les textes avec « … » → `views::ellipsize` + `Wrapping::None` + `clip`.

### Rendu, mémoire, performances

- **Rendu** (`apps/oxytone/src/main.rs::configure_renderer`) : wgpu, `WGPU_BACKEND=dx12` sous Windows (OpenGL plante au démarrage : 0xC0000005 ; Vulkan : 226 Mo au lieu de 139) et `WGPU_POWER_PREF=low`, vsync. `antialiasing(false)` : l'appli ne dessine aucun tracé et le MSAA ×4 coûtait une image quatre fois plus grande. `set_var` est `unsafe` en Rust 2024 (autorisé seulement là).
- **Mémoire** (release, accueil chargé, 2026-10-30) : 134 Mo privés au repos, dont ~99 Mo dès l'ouverture de la fenêtre (socle wgpu/DX12) ; pic ~155 Mo pendant le décodage des images. Le worker Python (~100 Mo) et mpv (~38 Mo) sont des processus à part.
- **Pochettes** (`app/covers.rs`) : `Covers::get_rgba` décode en tâche de fond (source 240 px pour ≤ 200 px demandés, sinon 1 200 px ; 2 décodages à la fois), `image::Handle::from_rgba`, cache `(cover_id, taille)`. Tailles : `THUMB` 96, `CARD` 200, `HERO` 512. Budget 64 Mo pour les pochettes **libérables** (lignes de listes virtualisées, préchargement de fond, grandes pochettes), les moins récentes d'abord ; jamais une pochette affichée (`visible_covers`), ni celle du morceau en cours et de la page. Les autres demandes (`want_cover` : profil, cartes) restent : libérer ces dernières faisait disparaître la photo de profil et les cartes. La grande pochette de la page est redemandée à chaque visite. Un échec de chargement retire l'entrée (une prochaine demande retente).
- **Identifiants de pochette stables** : `oxytone_media::normalize_url` ignore le suffixe de taille des images Google (`=w120-h120…`) et les paramètres signés des vignettes `i.ytimg.com` (`?sqp=…&rs=…`, différents à chaque réponse pour la même image) ; avant, toute une playlist se rechargeait à chaque mise à jour.
- **Accueil** : pochettes demandées par rangée visible (+ une d'avance) au fil du défilement (`want_home_covers`), pas les ~140 d'un coup.
- **Virtualisation** : lignes de hauteur fixe (`ROW_H` 58, `QROW_H` 50), en-tête de playlist de hauteur fixe, `visible_range` + `virtual_list` ; pochettes des lignes visibles demandées 120 ms après l'arrêt du défilement (`CoversSettle`).
- **Défilement animé** (`smooth.rs`) : `WheelCatcher` intercepte les crans de molette et anime la position via `window::frames()` (abonnement actif seulement pendant une animation) ; `glide_to` pour les paroles (plus lent). Shift + molette = rangées horizontales.
- **Images/s** : `OXYTONE_FPS=1`. Mesuré : ~210 im/s en fenêtre 1650 × 1050, 150-165 en plein écran 2560 × 1440 (proportionnel aux pixels).

### Pages et comportements

- **Navigation** : une page à charger (album, artiste, playlist hors cache) n'est affichée qu'une fois prête (`pending_route`, barre animée par-dessus la page) ; une playlist dès sa 1re page. Recherche : résultats montrés d'un coup quand toutes leurs pochettes sont là (garde-fou 6 s).
- **Accueil** : la page d'accueil de YouTube Music, **figée pendant la session** (demande de l'utilisateur : le cache s'affiche au lancement, la version fraîche n'est qu'enregistrée pour le prochain lancement). Salutation sur un dégradé vertical de la teinte ; « Réécouter » en mosaïque 4 × 4 (2 colonnes si la colonne centrale fait < 760 px, albums / playlists / EP / artistes seulement) ; « Tes playlists » ; les autres rangées de YouTube. Bouton lecture rond au survol des cartes (`views::cover_with_play`, `Message::PlayItem`).
- **Lancer un morceau = double-clic** (demande de l'utilisateur) : lignes, file et cartes de morceaux sont des `mouse_area`, pas des boutons. Clic simple = sélection (fond renforcé + liseré), Ctrl + clic = ajouter / retirer, Maj + clic = plage (`App::current_list` d'après la page). Clic droit sur la sélection = menu groupé (`Target::Tracks`).
- **Nom d'un morceau** (`views::track_title`) : ouvre sa page (album ou single). La grande vue « En cours » s'ouvre seulement par la pochette de la barre du bas.
- **Glisser-déposer** : appui sur une ligne → `TrackDrag` (la sélection si la ligne en fait partie) ; au-delà de 8 px, c'est un glissement (étiquette qui suit la souris). Cibles (`views::drop_zone`) : file, titres likés, playlists du compte. Dans la file : appui + déplacement = réordonner (`QueueDrag`), double-clic = lancer ; rien ne passe devant le morceau en cours.
- **File** : sélection par `QueueId` (elle suit le morceau), retirée au changement d'aléatoire ; la file remélangée apparaît en fondu de haut en bas (`anim::QueueFade`). Un glissement de chaque ligne vers sa nouvelle place a été essayé puis refusé.
- **Tri des playlists** (`PlaylistSort`) : ordre, titre, artiste, album, durée ; second clic = inverse. Pas de flèches (demande de l'utilisateur) : « · A–Z / Z–A », « · courts / longs ».
- **Bibliothèque** : bouton lecture au survol sur toutes les cartes (playlists, albums, artistes), comme à l'accueil. `library::sorted_order` (lecture : toute la playlist dans l'ordre affiché) et `view_order` (tri + recherche : lignes, sélection avec Maj, pochettes visibles).
- **Panneau de droite** : la file **ou** les paroles (`RightPanel`, bouton micro). Paroles : fond teinté par la pochette, texte blanc gras 20 px, opacité 1 / 0,5 / 0,3 (chantée / à venir / passée), survol = texte plus clair sans cadre, clic = aller à ce moment ; hauteur de chaque ligne estimée d'après sa longueur (`lyric_heights`, même calcul pour l'affichage et le défilement) ; la ligne chantée glisse aux deux cinquièmes du panneau ; molette = suivi suspendu 4 s ; « Chargement… » pendant la recherche.
- **Vue « En cours »** (mode focus, « comme au cinéma ») : pochette HD à la taille de l'écran (`big_size` : 800 ou 1 200 px selon `np_cover` × `scale_factor` ; 512 agrandi paraissait flou ; vignettes vidéo en `maxresdefault` si elle existe), libérée en quittant la vue ; l'ancienne reste jusqu'à ce que la nouvelle soit prête en HD (`NP_HD_WAIT` 3 s), puis, fondu de 0,7 s entre deux pochettes (`np_art`, `np_fade`, déclenché dans `aim_anims` quand la nouvelle est prête), titre long sur deux lignes ; composition centrée dans la fenêtre (demande : pas tout à gauche) ; pochette à 52 % de la hauteur (`np_cover`, 280-620 px) et titre / artiste / album à gauche, paroles en 32 px (`NP_LYRIC_SIZE` ; `lyric_heights` prend la taille) sur ≤ 960 px à droite, paroles synchronisées à droite (`views::lyrics_body` avec `interactive = false` : ni clic, ni barre, molette ignorée ; défilement `NP_LYRICS_SCROLL` piloté seulement par `follow_lyrics`). Pas de « À suivre » (retiré à la demande de l'utilisateur). Paroles seulement si **synchronisées** ; sinon pochette et titre seuls, au centre. Passage de l'un à l'autre animé (`np_split` 0 → 1 en 0,65 s : la pochette glisse, les paroles apparaissent en fondu dans un conteneur qui s'élargit, contenu de largeur fixe) ; rien ne bouge tant que les paroles du nouveau morceau chargent (`np_lyrics_known`). Rien n'apparaît au mouvement de la souris ; un clic affiche / masque la barre de contrôles, posée *par-dessus* le bas de la page en fondu (260 ms), marge du bas réservée ; Échap pour revenir.
- **Plein écran (F11) sous Windows** : fait main (`oxytone_os::fullscreen`) ; le plein écran de winit, sur une fenêtre sans cadre, réappliquait à la sortie un style mémorisé (vieux cadre Windows 7 dès la 2e fois). Une fenêtre agrandie est d'abord repassée en taille normale (sinon bornée à la zone de travail), étendue sur `rcMonitor` et déclarée à la barre des tâches (`ITaskbarList2::MarkFullscreenWindow`). Ailleurs : `window::set_mode`.
- **Barre de titre maison** (`chrome.rs`, `decorations: false`), même fond que les barres latérales : glisser = `window::drag`, double-clic = agrandir, bords invisibles de 5 px = `drag_resize`. Cachée seulement en plein écran.
- **Menu clic droit** (`context.rs`) : `mouse_area::on_right_press` dit la cible ; la position vient de `PointCatcher` posé autour de toute la fenêtre ; le menu est la couche la plus haute, dans le repère de la fenêtre. Icône par action. Radio d'un titre : s'il est en cours, il continue ; puis `ClearUpcoming` **puis** `Enqueue` (chaînés : deux `send` en parallèle n'ont pas d'ordre garanti).
- **Suggestions de recherche** : panneau `opaque` posé par-dessus la navigation, juste sous le champ.
- **Recherche** : onglets Tout / Titres / Albums / Artistes (`SearchTab`) ; recherches récentes (`cache_dir/library/recent_searches.json`, 12) enregistrées sur Entrée, en ouvrant ou en lançant un résultat, montrées quand le champ est vide.
- **Minuteur de sommeil** : icône lune de la barre (menu ouvert au point du dernier clic gauche, `Ctx::LeftPoint`) : 15 / 30 / 45 / 60 min ou fin du morceau ; le volume baisse sur les 30 dernières secondes (`SLEEP_FADE`) puis pause et volume rendu.
- **Ctrl + Z** : remet le dernier morceau retiré de la file (`undo_removed`, 20) : `Enqueue` puis `Move` à son ancienne place quand la file revient.
- **Onglet Téléchargements** (Bibliothèque, `collection::downloads_tab`) : tailles (`offline_sizes`, relevées par `scan_offline`), playlists téléchargées et titres, tri nom / taille, retrait, « Tout supprimer ».
- **Nouveautés des artistes** (`releases.rs`) : toutes les 12 h, pages des 40 premiers artistes suivis (4 à la fois), sorties de l'année (et de l'année passée en janvier-février), 2 par artiste ; `cache_dir/library/releases.json` (avec les sorties déjà signalées) ; rangée de l'accueil et message pour une sortie nouvelle (pas au premier passage).
- **Paroles** (Paramètres) : taille en mode focus (`NP_LYRIC_SIZES`), romanisation : `Lyrics::romanized` calculé dans le catalogue (`romanize.rs`) : romaji de NetEase (`rv=-1`, `romalrc`, aligné à ±1 s), sinon kana (`yomikata-core`), hangul (règles), pinyin (`pinyin`). Pas de dictionnaire de kanji : `kakasi` est GPL, lindera embarque ~50 Mo. `lyric_heights` prend la longueur de la romanisation.
- **Apparence** (Paramètres) : accent fixe (7 couleurs) ou pochette (`fixed_accent`, appliqué dans `aim_anims`) ; fond noir ou anthracite (`style::set_anthracite` : `bg()`, `surface()`… sont des fonctions ; `ON_ACCENT` pour le texte des boutons pleins).
- **Statistiques** : récap du mois (`stats::recap` : artiste et titre du mois, découvertes = artistes entendus pour la première fois, heure préférée).
- **Raccourcis** (`app/keys.rs`, aide sur `?`) : Espace, ← / → (5 s), Ctrl + ← / → (précédent / suivant), ↑ / ↓ (volume ± 5), M (muet), L (like de la sélection ou du morceau en cours), / ou Ctrl + F (recherche), F11, Échap (ferme / désélectionne, sinon **remonte en haut de la page** sans la quitter, demande de l'utilisateur ; ne quitte que la vue « En cours »).
- **Animations** (`anim.rs`) : `App::update` appelle `aim_anims` après chaque message ; bandes de l'égaliseur, volume, saut de la barre de progression et interrupteurs rejoignent leur valeur en ~150 ms (la position qui avance seule n'est pas animée). Teintes : tout suit `accent` (morceau en cours) ; seul le dégradé en haut d'une page suit `page_accent` ; fondu de 0,6 s.
- **Bibliothèque** (`collection.rs`) : onglets Playlists / Albums et EP / Artistes, tri (récents, A → Z, auteur / abonnés), caches `albums.json` / `artists.json` (30 min). Playlists des autres : ni renommage, ni suppression, ni retrait.
- **Playlists** : `Account::playlist_progressive` envoie chaque page de 100 titres dès réception ; cache disque `cache_dir/library/` (version en cache affichée tout de suite, fraîche substituée). Rechargement : playlists 30 min, likes 1 h, bouton ↻ pour forcer. À la fin d'une mise à jour, l'adresse de la pochette d'en-tête est gardée si c'est la même image.
- **Historique** : `Route::History`, ouvert par le profil ou les Paramètres, redemandé à chaque ouverture.
- **Paramètres** : égaliseur (curseurs `style::eq_slider`), volume homogène, qualité, sortie audio (`pick_list`), hors ligne, arrière-plan (icône), notifications, stockage, compte (historique, **import Spotify** : le bouton est ici seulement, demande de l'utilisateur).
- **Stockage** : « Cache d'écoute » (fichiers non épinglés, vidable) et « Téléchargements » (épinglés, `pinned.json`) comptés à part (`settings::audio_usage`). « Données Internet » : son reçu (`oxytone_player::traffic` : taille des fichiers lus depuis Internet par mpv, observée via `path` / `file-size`, + téléchargements du cache) et pochettes (`oxytone_media::traffic_bytes`) ; total par mois dans `cache_dir/library/traffic.json`, mis à jour à l'ouverture des Paramètres et à la fermeture. Les requêtes du catalogue (quelques Ko) ne sont pas comptées.
- **Nouvelle playlist** : créée tout de suite sous le nom « Nouvelle playlist », ouverte, champ de renommage actif (plus de fenêtre qui demande le nom).
- **Fondus** : au changement de morceau, titres et pochette de la barre et du mode focus en fondu (`TRACK_FADE`) ; paroles du morceau quitté figées puis estompées (`lyrics_out`, `LYRICS_OUT`), retour en haut ensuite (`Message::LyricsReset`), nouvelles paroles en fondu (`lyrics_in`, `LYRICS_IN`) ; plus de « Chargement… ». Ligne chantée qui s'allume et précédente qui s'éteint en `LINE_FADE` (`lyrics_prev_line`, `lyrics_line_at`). Tout passe par `App::lyrics_on_screen`. Ordre des boutons d'en-tête : Lecture, Aléatoire, Télécharger, puis icônes. Interrupteurs maison (`settings::switch`).

## Intégration OS (`oxytone-os`)

- **Touches média + overlay** : souvlaki (SMTC sous Windows, MPRIS/zbus sous Linux) sur un fil dédié, HWND fourni par la GUI.
- **Barre des tâches Windows** (`taskbar.rs`) : boutons précédent / lecture-pause / suivant sous l'aperçu (`ITaskbarList3::ThumbBarAddButtons`) + sous-classement de la fenêtre (`SetWindowSubclass`, sur le fil de la fenêtre : depuis `native_handle`) ; le fil de `oxytone-os` poste `WM_APP+0x31` pour changer lecture / pause. Icônes dessinées en code. Reposées sur `TaskbarButtonCreated`.
- **Notifications** (`notify-rust`) : avec la pochette (fichier JPEG du cache, `Covers::jpeg_file`, cache passé par `NotifySettings::covers`), à chaque nouveau morceau si la fenêtre n'a pas le focus (réglable, `ui.json`). Windows : AUMID `oxytone.player` déclaré dans `HKCU\Software\Classes\AppUserModelId` (sinon la bulle porte le nom de PowerShell).
- **Plein écran Windows** : `fullscreen.rs` (voir GUI).
- **Lancement** (`apps/oxytone/src/main.rs`) : PATH relu dans le registre (`refresh_path`, l'Explorateur garde celui de l'ouverture de session) et dossier de travail = dossier de l'exe (celui de l'installateur, temporaire, est supprimé : Windows refusait alors de lancer mpv). `deps::find` : repli sur les emplacements habituels (scoop, Program Files) et raison d'un échec au journal. Démarrage rapide (`fast_start_client = "android"`) par défaut sans compte : sinon ~5 s d'attente imposées par YouTube au premier morceau.
- **Instance unique** (`oxytone_gui::instance`) : la première instance écoute sur `127.0.0.1:26541` ; un deuxième lancement s'y annonce (`oxytone-show`), autorise le premier plan (`AllowSetForegroundWindow`), la première ramène sa fenêtre (`tray::show`) et la seconde s'arrête.
- **Discord** (`discord.rs`, crate `discord-rich-presence`) : fil dédié, statut « Écoute » (titre, artiste, pochette par URL ≤ 256 caractères, temps restant), effacé en pause ; reconnexion toutes les 20 s si Discord est fermé. Il faut l'**Application ID** d'une application créée par l'utilisateur sur discord.com/developers (champ des Paramètres, `ui.json`).
- **Zone de notification** (`tray.rs`, réglage « Arrière-plan », `ui.json` `tray`) : `Shell_NotifyIconW` sur la fenêtre principale ; ses messages (`WM_APP+0x40`) passent par le sous-classement de `taskbar.rs`. Clic = afficher, clic droit = menu (lecture / pause, suivant, précédent, afficher, quitter). Icône dessinée en code (rond rouge, triangle blanc). Fermer la fenêtre avec l'icône active = `ShowWindow(SW_HIDE)` ; « Quitter » pose `QUIT` puis poste `WM_CLOSE` (arrêt normal de mpv). Reposée sur `TaskbarButtonCreated`. Windows seulement.
